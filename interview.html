Q1 什么是 Token？为什么同样的中文内容，Token 数差别很大？ 基础

参考答案：Token 是模型处理文本的最小单位，由分词器（Tokenizer）通过 BPE 等算法切分得到，并不等于「字」或「词」。一个中文汉字通常占 1–2 个 Token，英文常见单词约 1 个 Token。

Token 数差异大的原因主要有三：

  • 分词器词表覆盖度不同——词表里没有的词汇会被拆成多个子词
  • 标点、空格、特殊符号、代码片段往往分词效率低
  • 不同模型的训练语料结构不同（中文语料占比高的模型，中文分词更紧凑）

追问方向：上下文窗口与 Token 成本如何换算？如何为长文档场景做 Token 预算？

Q2 自注意力的计算复杂度是多少？工程上如何优化长序列？ 进阶

参考答案：标准自注意力的时间与显存复杂度都是 O(n²d)（n 为序列长度，d 为维度），这是长上下文的主要瓶颈。

常见优化路径：

  • 稀疏/滑窗注意力，只计算局部或关键位置
  • FlashAttention 等 IO 感知实现，降低显存访问开销
  • KV Cache 复用与量化，减少增量推理的重复计算
  • 线性注意力、状态空间模型等替代结构

追问方向：KV Cache 为什么会成为显存瓶颈？PagedAttention 解决了什么问题？

Q3 Temperature、Top-p、Top-k 分别控制什么？线上服务怎么设置？ 基础

参考答案：三者都作用于解码阶段的采样分布。Temperature 缩放 logits 调节整体随机性；Top-k 只保留概率最高的 k 个候选；Top-p 保留累计概率达到 p 的最小候选集合。

实践经验：需要稳定输出的抽取、分类、工具调用场景，温度调到 0–0.2，并优先用结构化输出约束；创意写作可放宽到 0.7–1.0。Top-k 与 Top-p 一般只调一个，同时打开容易互相干扰。

追问方向：温度设为 0 是否就一定可复现？还有哪些因素会造成结果不一致？

Q4 如何减少大模型的幻觉？有哪些工程手段？ 进阶

参考答案：可以从四层入手：

  • 输入层：用 RAG 提供可靠上下文，并明确要求「仅依据给定资料回答」
  • 提示层：要求先引用原文再给结论，允许回答「资料中没有提及」
  • 解码层：降低温度、限制输出格式、要求结构化字段
  • 校验层：加一道一致性检查或小模型复核，关键结论做事实核对

追问方向：如果检索到的资料本身就是错的，怎么办？

Q5 描述一个完整的 RAG 链路，并说明每个环节常见的失效点 进阶

参考答案：链路为「文档解析 → 切分 → 向量化 → 存储 → 检索 → 重排序 → 拼装上下文 → 生成」。

  • 解析：表格、扫描件、多栏排版容易丢结构
  • 切分：块太大引入噪声，太小丢失上下文，建议按语义或标题切分并加重叠
  • 向量化：领域术语与缩写表达不佳，可考虑混合检索补足
  • 检索：只用向量会漏掉精确关键词，建议 BM25 + 向量混合
  • 重排序：候选多时用 Cross-Encoder 精排，收益明显但要注意延迟
  • 生成：上下文过长会被稀释，需要控制在有效区间

追问方向：如何量化评估 RAG 效果？召回率和答案准确率是什么关系？

Q6 向量数据库怎么选？什么场景其实不需要它？ 基础

参考答案：选型主要看数据规模、并发、运维成本与是否需要混合检索。

  • 数据量在几十万条以内、已有 PostgreSQL，直接用 pgvector 最省事
  • 需要高性能与水平扩展，选专用向量库（Milvus、Qdrant 等）
  • 需要复杂过滤与事务，优先考虑支持标量过滤的方案

不需要向量库的场景：候选集只有几百条时，关键词检索加规则过滤往往更快更准；纯结构化查询用 SQL 更合适。

追问方向：HNSW 与 IVF 索引的取舍是什么？

Q7 Agent 与普通 LLM 应用的本质区别是什么？ 基础

参考答案：普通应用是「一次输入 → 一次输出」的静态链路；Agent 引入了自主决策循环——模型根据目标决定下一步做什么、调用哪个工具、要不要继续，直到任务完成或触发终止条件。

关键组成：LLM（决策核心）、工具（行动能力）、记忆（状态延续）、规划（任务分解）与终止条件。

追问方向：如何避免 Agent 陷入死循环？预算与步数上限怎么设计？

Q8 多 Agent 协作有哪些常见模式？什么时候不该用多 Agent？ 高阶

参考答案：常见模式包括：

  • Planner-Executor：一个负责拆解，一个负责执行
  • Critic/Reviewer：增加评审角色，提升输出质量
  • Router：按意图分发到不同专家 Agent
  • Debate：多角色讨论后收敛结论

不该用的场景：任务本身是线性的、状态简单；或者延迟与成本敏感。多 Agent 会显著增加 Token 消耗与不确定性，很多时候单 Agent 加更好的工具就够了。

追问方向：多 Agent 之间如何共享上下文而不炸掉窗口？

Q9 什么情况下应该微调，而不是用 RAG 或 Prompt？ 进阶

参考答案：按需求性质判断：

  • 缺知识（模型不知道某事实）→ RAG，知识可更新、可追溯
  • 缺格式与风格（输出不符合规范）→ 先改 Prompt，仍不稳定再微调
  • 需要固定行为模式、降低提示词长度、压缩成本 → 微调更合适
  • 需要极致延迟或数据不出域 → 微调小模型自部署

追问方向：LoRA 与全参微调的取舍？数据量多少才值得微调？

Q10 线上推理的吞吐和延迟如何优化？ 进阶

参考答案：从三个层面下手：

  • 调度层：连续批处理（Continuous Batching）提升 GPU 利用率，PagedAttention 减少显存碎片
  • 模型层：量化（INT8/INT4）、蒸馏、投机解码
  • 业务层：结果缓存、按难度分流到不同规格模型、流式输出改善首字延迟体感

衡量指标要同时看首 Token 延迟（TTFT）与每 Token 输出时间（TPOT），只优化吞吐可能让单请求变慢。

Q11 设计一个企业知识库问答系统，你会怎么拆？ 高阶

参考答案：按四层拆：

  • 数据层：多源接入（文档库、Wiki、工单），解析清洗、权限标注、增量更新
  • 检索层：混合检索 + 重排序，按用户权限过滤，缓存高频问题
  • 生成层：上下文拼装、引用标注、拒答策略、多轮改写
  • 运营层：评测集与回归、badcase 归集、成本与延迟监控、灰度发布

要点：权限必须贯穿到检索阶段，而不是生成后再过滤；没有评测集的系统无法迭代。

追问方向：如何做增量更新而不重建全量索引？

Q12 Token 成本突然翻了三倍，你会怎么排查？ 进阶

参考答案：建立 Token 级追踪后按维度下钻：

  • 按接口/场景拆：是某个新功能带来的，还是全量上涨
  • 按环节拆：输入 Token 涨（上下文变长/重复注入）还是输出涨（回答变啰嗦/循环调用）
  • 按模型拆：是否发生了模型路由变更或降级回退
  • 按调用次数拆：是否出现重试风暴、Agent 步数失控

常见根因：Prompt 模板膨胀、历史对话未做裁剪、检索块数变更、缓存失效。

Q13 业务方要求「一周内上线一个 AI 客服」，你怎么推进？ 高阶

参考答案：先对齐范围再谈技术。

  • 定边界：只做高频问题的自动应答，复杂问题转人工，明确成功率目标
  • 拿数据：从历史工单里抽出 100–200 条真实问题，作为评测集与知识来源
  • 搭最小闭环：RAG + 拒答策略 + 转人工兜底，先保证不出错
  • 建度量：准确率、转人工率、用户反馈，一周内跑通数据回流
  • 渐进放量：先小流量灰度，badcase 归集后再优化

关键判断：宁可答不出，也不要答错——客服场景的错误成本远高于拒答。
