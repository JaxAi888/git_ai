Agent 架构设计 工程实践

从 0 到 1 搭建多 Agent 协作系统：Planner-Executor-Critic 实战

AIJax · 2026-09-14 · ⏱️ 18 min 阅读 · 👁️ 12.4k · ❤️ 532

过去半年，我负责把一个「单 Agent 跑通 Demo」的系统推到生产环境。这篇文章记录完整的工程化过程：任务怎么拆、上下文怎么共享、失败怎么兜底，以及三个文档里不会写、但上线一定会撞上的坑。

为什么单 Agent 不够用

单 Agent 不是不能做，而是边界很快会到：

  • 上下文窗口爆炸：工具越多，系统提示词越长，检索类工具再回灌大段文档，窗口很快见底；
  • 职责耦合：规划、执行、检查挤在一个提示词里，模型在不同「人格」间切换，稳定性肉眼可见地下降；
  • 无法并行：三个独立子任务只能串行跑，延迟直接相加。

结论很朴素：当任务能被拆成「相对独立的子目标」时，多 Agent 才有收益；拆不开就别硬拆。我用一条判断标准——子任务之间是否需要频繁交换中间结果。交换越少，拆分收益越大。

整体架构：Planner-Executor-Critic

我们最终采用的三角色架构，是所有变体里最经得住折腾的一版：

  • Planner：只做一件事——把目标拆成带验收标准的子任务，输出结构化 DAG；
  • Executor：领取子任务，带着裁剪后的上下文去调用工具，只关心当前节点；
  • Critic：对着验收标准检查产出，不通过就打回重做（带失败原因），最多重试 N 次。
python · 主循环骨架
class Orchestrator:
    def run(self, goal: str) -> Result:
        plan  = self.planner.decompose(goal)      # ① 拆任务 → DAG
        state = SharedState(plan)                # ② 共享黑板

        for node in plan.ready_nodes():           # ③ 只取无依赖节点
            ctx = state.compact_context(node)      #    按需裁剪上下文
            for attempt in range(3):              #    最多重试 3 次
                output = self.executor.run(node, ctx)
                verdict = self.critic.review(node, output)
                if verdict.ok:
                    state.commit(node, output)          # ④ 落库 + 广播
                    break
                ctx = ctx.append(verdict.feedback)    #    失败原因回灌
            else:
                return state.escalate(node)          # ⑤ 兜底降级

        return state.final()
💡
关键设计：Planner 拆出的每个子任务都自带「验收标准」字段。Critic 只对照标准打分，不重新理解目标——这让审查环节的误判率降了一个量级。

任务分发：把大目标拆成可验证的小任务

拆任务最大的坑是拆得太碎：碎到每个子任务都失去语义，Executor 反而做不好。我们的经验值是一个子任务对应一次工具调用 + 一次判断，再大就继续拆，再小就往上合。

Planner 的输出是严格的 JSON（用 function calling 约束，别指望提示词能稳定住格式）：

json · Planner 输出
{
  "nodes": [
    {
      "id": "search",
      "task": "检索近 90 天相关工单",
      "tool": "ticket_search",
      "acceptance": "返回 ≥ 10 条且均为已关闭状态",
      "depends_on": []
    },
    {
      "id": "cluster",
      "task": "按根因聚类并输出 Top3",
      "tool": "analyze",
      "acceptance": "Top3 覆盖 ≥ 60% 样本且有人工可读标签",
      "depends_on": ["search"]

上下文共享：三种方案与选型

多 Agent 的本质难题不是调度，是上下文。三种常见方案的适用面完全不同：

方案原理适合典型问题
共享内存所有 Agent 读写同一块黑板≤3 个角色、强同步写冲突、信息互相污染
消息传递节点间显式收发消息流水线式、链式依赖拓扑一复杂就难追踪
外部存储产出写库，按需检索回灌长任务、跨会话检索质量决定一切

我们最后是混合的：DAG 状态走共享内存（结构化、可版本化），大块产出（检索结果、长文档）走外部存储，执行时按依赖裁剪回灌。核心就一个函数：compact_context(node)——只带「本节点依赖的产出摘要 + 失败反馈」，其余一律不带。

一条铁律：上下文只增不减是慢性死亡

任何「把全部历史塞给下一个 Agent」的写法，都会在两周后变成不可解释的玄学系统。我们的黑板记录里，单节点上下文压缩后超过 4k token 就会告警——超限通常说明任务拆分粒度错了，回去重新拆，而不是换个更贵的模型。

失败重试与兜底

重试不是简单的 for 循环，重点是把 Critic 的失败原因回灌给 Executor——不带反馈的重试等于让模型再掷一次骰子：

  • 第 1 次失败：回灌 Critic 的具体不合格项（如「Top3 未覆盖 60% 样本」）；
  • 第 2 次失败：降温度 + 换更详细的 few-shot 示例；
  • 第 3 次失败：escalate() 兜底——输出「该节点失败 + 已完成部分 + 人工介入建议」，绝不静默吞掉。
⚠️
踩过的雷：早期版本失败三次后自动「编造一个看起来合理的结果」继续往下跑，下游全被污染。生产系统的原则是——宁可部分完成并如实上报，不要伪造完整。

三个真实踩坑

坑一：上下文爆炸导致「选择性失忆」

现象是 Critic 对着验收标准却「看不见」——因为整段标准被挤到窗口边缘被截断了。教训：验收标准这类关键信息永远放在上下文末尾（利用 recency），并且用日志记录每个节点的实际 token 构成，出问题能一眼定位是哪一段撑爆的。

坑二：幻觉工具参数

Executor 会编造不存在的参数名和枚举值，工具层一校验就崩。两层解法：接口侧用 pydantic 严格校验 + 参数错误信息原样回传给模型重试；提示侧在工具描述里写清「非法参数会返回错误对象」。上线后这类失败从 7% 降到 0.3%。

坑三：Planner-Executor 死循环

Critic 打回 → Executor 重做 → 又被打回，隐性死循环。除了 3 次重试上限，还加了一条熔断：同一个节点的失败原因如果两次相同，直接升级为「任务拆分问题」交回 Planner 重拆，而不是继续为难 Executor。

这三个坑的共同点：都在「模型能力」之外，属于纯粹的工程问题。多 Agent 系统的稳定性，八成取决于工程约束，两成才是提示词。

评测与上线

上线前我们只维护两个评测集，但每项都必须过：

  • 拆解质量：50 个目标的 Planner 输出，人工标注子任务可执行率（目标 ≥ 92%）；
  • 端到端成功率：100 个真实历史任务回放，全链路无人工干预完成率（目标 ≥ 85%）。

上线后靠可观测性续命：每次模型调用的 token 构成、重试次数、熔断次数全部上报，多 Agent 系统没有仪表盘等于裸奔。这套的完整实现我放在了 大模型应用开发项目 里的 agent-orchestrator，欢迎白嫖。

写在最后：多 Agent 不是银弹，它只是把「一个复杂的提示词」变成「一组可分别测试、分别约束的小系统」。积硅步，致千里——先把单 Agent 的每一步做可靠，拆开才有意义。
